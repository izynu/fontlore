# SaaS, Ebook, and Embedded Use

What this reference covers: The licensing picture for server-rendered and embedded contexts: SaaS platforms generating documents and images, ePub embedding, kiosk and console deployments, and the signals that mean it is time to talk to the foundry directly instead of clicking through a marketplace.

Marketplace license forms assume a person designing things and a website showing them. SaaS rendering, ePubs, and devices break those assumptions, and the correct answer is usually a conversation.

The conversation goes better with numbers: contexts inventoried, volumes estimated, entities named. This reference is the checklist for building that one-pager.

## SaaS rendering

- Server-side rendering (generating PDFs, images, invoices, certificates with fonts on a server) is not desktop use and not webfont use; it is its own category.
- Some licenses explicitly cover "server-side embedding" or "application service provider" scenarios; many do not mention it, which means ask, not assume.
- The risk scale matters: rendering user-generated documents at scale (a contract platform stamping thousands of PDFs daily) is a different negotiation than an internal admin tool exporting ten PDFs a week.
- Open fonts dissolve the problem: an OFL font on the rendering server is legal with license retention, which is why so many document platforms run on open type.
- If a commercial font is required, foundries sell server or OEM licenses scoped by deployment size; expect custom terms rather than cart buttons.
- Containerized rendering counts too: scaling from three servers to forty Kubernetes pods changes the deployment-size math, so describe architecture, not machine counts, when asking.
- Batch jobs, cron renderers, and CI-generated PDFs are server rendering as well; the quiet nightly job is the classic unlicensed context.

## Where the SaaS lines sit

- Browser-side rendering of your UI (the SaaS dashboard itself): ordinary webfont licensing usually covers this; confirm login-walled coverage for enterprise deals.
- User-triggered exports rendered server-side: server use.
- Fonts embedded in templates users download and take away: redistribution territory; usually forbidden without explicit rights.
- White-label deployments where customers rebrand your product: each deployment may need its own scope; write this into contracts.
- API-driven image generation (social cards, OG images): server rendering again; open fonts keep this frictionless.
- Admin and reporting surfaces used by your own staff: still webfont serving if they run in a browser; internal does not mean unlicensed.
- Customer-facing email generated by the SaaS (receipts, notifications): fonts in HTML email mostly do not render, so this is rarely a licensing question and always a design one.

## ePub embedding

- ePub files can carry font subsets that install or load on reading devices; that is distribution of the font software, governed by the license's ePub or electronic-publication clauses.
- OFL fonts: embedding subsets in ePubs is standard practice; keep the license text accessible per the license's redistribution terms when the font file is included.
- Commercial fonts: many foundries sell ePub rights per title or by sales tier; check whether the clause covers the formats (EPUB 3, fixed layout) you ship.
- DRM and format conversion do not change the licensing analysis; the font file travels either way.
- Educational publishing at scale is a negotiation; publishers standardize on open fonts precisely to avoid per-title math.
- Audiobook and app-book hybrids blur categories: an app that reads and displays the book is an app embedding conversation, not an ePub one.
- When a backlist title gets a new edition with a new font, treat it as a new licensing event; old clauses do not automatically extend.

## Kiosk, console, and TV

- Any device that ships with font files inside is embedded use: kiosks, POS terminals, game consoles, smart TVs, in-flight entertainment.
- Per-unit or per-deployment licensing exists at enterprise foundries; marketplace purchases almost never cover device bundling.
- Certification processes (console platforms) treat font licensing as part of legal submission; start the paperwork early.
- Firmware updates that add fonts create new distributions; keep the entitlement list current per release.
- Digital signage networks: licensing often scales by screen count or location count; inventory the fleet before negotiating.
- Menu boards and self-checkout terminals are the high-turnover embedded cases; franchise models multiply the entities involved, which the license must name.
- Embedded use in medical and industrial devices adds validation cycles; font changes after certification are expensive, so license headroom matters more than usual.

## When to contact the foundry

- You are embedding font files in anything distributed to users: apps beyond marketplace tiers, devices, kiosks, games on consoles.
- You render fonts on servers at meaningful scale or in a customer-facing product.
- You need rights the scope table does not mention: white-labeling, sublicensing to customers, worldwide OEM redistribution.
- You are modifying the font (custom cuts, additional glyphs) and need the derivative defined in the contract.
- Foundries respond well to precise questions: deployment counts, rendering volumes, territories. Vague questions get vague quotes.
- Bring a one-page description of the architecture: what renders where, at what volume, owned by which entity. Foundries answer that document, not the phone call.
- Ask for the answer as a license document amendment, not just an email; emails reassure, amendments bind.
- Price the alternatives in parallel: an open-font migration quote from your own team gives the foundry conversation a real anchor.

## Workflow

1. Inventory every context where fonts execute: browser, server, device, publication.
2. Tag each context with the license category it implies (web, desktop, server, embed, ePub).
3. For non-browser contexts with commercial fonts, list the deployment scale in numbers before contacting foundries.
4. Prefer open fonts for server and device layers unless the brand mandates otherwise; document the choice.
5. Keep written foundry answers with the license documents; they are part of the audit trail.
6. Re-inventory when the product adds a surface (an export feature, a hardware line, a reader app); new surfaces are new rows.
7. Review volumes against entitlements at the same cadence as the pageview tiers; embedded and server volumes drift the same way traffic does.

## Common mistakes

- Generating PDFs with desktop-licensed fonts on a production server because the license came with "unlimited installs".
- Shipping ePubs with embedded commercial fonts under a desktop license and discovering it at a platform review.
- Treating kiosk deployments as "just a big website" and skipping embedding licenses.
- White-labeling a product with embedded fonts without checking that the license permits customer deployments.
- Waiting until launch week to contact foundries; enterprise font deals take weeks, not hours.
- Pricing a kiosk fleet per store without asking what happens when stores close; unit-based terms usually survive churn better than site-based ones.
- Rendering marketing one-pagers with the same unlicensed server stack as invoices; the exposure is identical even when the stakes feel lower.
- Treating the ePub clause as transferable across formats; a clause for reflowable EPUB 3 says nothing about fixed-layout children's books.

## Decision rules

- Fonts execute outside the browser: identify the license category explicitly; there is no default.
- Scale is unbounded or user-generated: open fonts unless the brand absolutely requires otherwise.
- The deal involves OEM or redistribution rights: foundry-direct conversation, not a marketplace cart.
- When a context is genuinely ambiguous, the cost of asking is days; the cost of guessing is an incident.
- Prefer licensed-per-server over licensed-per-document when volumes are spiky; per-document deals punish marketing success.
- For white-label deals, put the font licensing obligations into the customer contract itself, not only into your vendor agreement.
- When the foundry's answer changes the architecture (a per-server license pushing you to consolidate renderers), record that constraint in the architecture docs, not just in the contract folder.

## Comparison table: context to category

| Context | License category | Typical pricing shape | Ask the foundry when |
| --- | --- | --- | --- |
| Browser UI of the SaaS product | Webfont | Pageview or flat tiers | Login walls are enterprise-scale |
| Server-generated PDFs and images | Server / application | Custom, volume-based | Volume is unbounded or user-triggered |
| ePub with embedded subsets | ePub clause | Per title or sales tier | Formats or DRM are unusual |
| Kiosk or POS device | Embedded / device | Per unit or per deployment | Fleet grows or firmware updates |
| Console game | App embedding plus cert | Per title | Submission is scheduled |
| White-label customer deployments | Embedding plus redistribution | Custom contract | Customers rebrand the product |
| Templates users download | Redistribution | Often unavailable | Users take files off-platform |

The table's use is triage: rows that say "custom" are rows where a marketplace cart is the wrong tool, and a conversation is the right one.

## Worked example: the document platform

A SaaS product generates contracts and invoices as PDFs, branded with a commercial serif. The licensing walk:

- Inventory: the browser UI uses the same serif as a webfont (covered), while a headless rendering service on three servers produces the PDFs (not covered by either the webfont or the desktop seats).
- The team sized the use honestly: about 40,000 documents monthly, growing with customers, each rendering the full family at several weights.
- Foundry conversations produced two options: a server license priced by deployment size, or migrating the rendering layer to an open serif with comparable texture (Source Serif 4 and Literata are the usual candidates in this scenario).
- The team chose the open serif for the server layer and kept the commercial family browser-side, where the webfont grant already applied; the mixed identity was acceptable because documents are print-facing and the web UI stayed on-brand.
- The migration was a design review, not a licensing event: metrics were compared, the template was retuned, and the change shipped behind a feature flag.
- The decision record lists the licensing delta (three-server license avoided), the design cost (one sprint), and the ongoing benefit (no per-server math as rendering scales).
- The pattern generalizes: in server-rendering contexts, the open-font option is usually cheaper than the license, and the license is usually cheaper than the guess.

## Questions to ask the foundry

- Is server-side rendering covered by any existing license we hold, and if not, what category does it fall under?
- How do you price rendering volume: per server, per document, per customer deployment, or flat?
- If our customers export branded documents containing the font, does that change the grant?
- Does the ePub clause cover both reflowable and fixed-layout formats, and DRM-wrapped deliveries?
- For device embedding, is the grant per unit shipped, per model, or per deployment site, and does it survive firmware updates?
- For white-label deployments, may our customers' entities render the font under our agreement, or does each need its own paper?
- What documentation do you need from us at contract time, and what do we owe you at renewal?

## Field notes

- The fastest de-risking move for SaaS rendering is standardizing the server layer on open fonts; it converts a recurring negotiation into a design decision.
- ePub rights are cheap relative to the exposure: a per-title clause costs less than one reprint run, and publishers who skip it are the ones who get caught in store reviews.
- Kiosk and signage fleets grow by acquisition as often as by purchase; write fleet growth into the contract so a bigger fleet is an invoice, not a breach.
- Console certification teams do read font paperwork; every studio that has failed a submission for missing font licenses has a story, and the stories all start with "we thought the desktop license covered it".
- If a customer demands your SaaS render in their brand fonts, that demand is a licensing conversation with the foundry, priced and scheduled like any integration.
- Keep rendering volumes in the license register; "about 40k documents monthly" written down today is the number that makes next year's renewal painless.
- When a platform (a reader, a store, a console) changes its embedding requirements, treat it as a trigger for a scoped audit; platform rules and font licenses drift independently.
- Trials and evaluation licenses almost never cover any of these contexts; the conversation with the foundry is also the exit from trial limbo.

## Quick reference: the context audit in five questions

1. Where does the font execute: browser, server, device, publication?
2. Who owns each execution point, legally: our entity, a customer's, a platform's?
3. What volume: pages, documents, units, titles?
4. What does the current grant name explicitly for each of the above?
5. What is written down, and what is only remembered?

The five answers, one page, is the artifact that turns a vague embedded-use worry into a scoped contract or a documented open-font decision.

## Field notes

- The single most common SaaS licensing shape that works: open fonts everywhere the machine renders, brand face only where the browser renders, and a written answer for anything else.
- Document generation libraries (PDF toolkits) bundle their own fonts for defaults; inventory those too, because "it came with the library" is not a grant.
- Keep an exit note per embedded context: if the product sunsets the ePub line or the kiosk fleet, the license line item should sunset with it.
